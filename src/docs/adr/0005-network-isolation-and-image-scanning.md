# ADR 0005: Сетевая изоляция, профили ядра, rootless-хосты и пересканирование образов

## Дата: 19-11-2026

## Статус: Accepted

## Контекст

ADR 0004 ограничил то, что процесс может сделать внутри своего контейнера. Оставались пути, которые не зависят от этих ограничений:

1. **Сеть.** Все сервисы сидели в одной default-сети compose. redis без пароля был доступен любому контейнеру стека, у `migrate` и `seed` был выход в интернет, а `web` публиковал порт на всех интерфейсах хоста. Админка SQLAdmin пока без логина (ROADMAP D4), значит любой, кто дотянется до порта 8000, видит персональные данные.
2. **Профили ядра.** seccomp и AppArmor по умолчанию были включены, но ничто не мешало отключить их правкой compose (`seccomp:unconfined`, `privileged: true`) или смонтировать Docker socket.
3. **Хост.** При rootful Docker выход из контейнера — это root на хосте.
4. **Уязвимости.** Образ не публиковался и не сканировался. Новые CVE появляются в образах, которые были чистыми в момент сборки: torch, numpy, системные библиотеки Debian.

## Решение

Принято решение изолировать сервисы по сетям, проверять политику безопасности compose в CI, поддерживать rootless-хосты и публиковать образы в GHCR со сканированием в каждой сборке и еженедельным пересканированием.

### Детали реализации

1. **Сети.** `backend` (`internal: true`, без выхода в интернет) — redis, web, bot. `edge` — только тем, кому нужен внешний мир: bot (Telegram API), model-init (Hugging Face), web (публикация порта). У `migrate` и `seed` `network_mode: none`. `web` работает с `HF_HUB_OFFLINE=1`.
2. **Порты.** `web` публикуется на `127.0.0.1` (`WEB_PUBLISH` для явного переопределения). redis не публикуется.
3. **Политика как код.** `scripts/ci/check_compose_policy.py` проверяет нормализованный `docker compose config` (prod и dev) и запрещает `privileged`, `cap_add`, host-namespaces, `seccomp/apparmor=unconfined`, `label=disable`, Docker socket и `/` в томах, сервисы без `cap_drop: ALL` / `no-new-privileges` / `read_only` (кроме dev с `develop.watch`), порты на всех интерфейсах, хранилища вне internal-сетей. Каждое правило покрыто тестом.
4. **Рантайм.** В CI внутри контейнера проверяется `Seccomp: 2`, `NoNewPrivs: 1`, `CapEff: 0`; в отчёт пишется `docker info` → SecurityOptions.
5. **Rootless.** Job `podman` собирает и проверяет образ в rootless Podman, включая то, что uid 10001 в контейнере не root на хосте. README описывает развёртывание на rootless Docker или Podman и требования (cgroup v2 с делегированием, subuid, порты ≥ 1024).
6. **Публикация.** После релиза `publish-image` пушит `ghcr.io/<owner>/university-match:vX.Y.Z` и `:latest` с SBOM и provenance (`mode=max`), создаёт подписанную аттестацию (`actions/attest-build-provenance`) и дописывает digest в GitHub Release.
7. **Сканирование.** Trivy из образа, закреплённого по digest, в каждой сборке: полный отчёт в summary, падение на CRITICAL/HIGH с доступным исправлением. `rescan.yml` каждый понедельник сканирует три последних выпущенных образа, загружает SARIF в Code scanning (категория на релиз) и падает на тех же условиях. Принятые риски — в `.trivyignore.yaml` с причиной и сроком.

## Альтернативы

* **Пересобирать образ из тега вместо реестра:**
  * *Плюсы:* не нужен реестр и права `packages: write`.
  * *Минусы:* сканируется реконструкция, а не тот образ, который реально запущен; нет digest, по которому можно проверить развёрнутое.

* **Grype или Docker Scout вместо Trivy:**
  * *Плюсы:* сопоставимое качество базы; Scout встроен в Docker.
  * *Минусы:* Trivy одним инструментом даёт SARIF, `--ignore-unfixed` и файл исключений со сроком; Scout требует аккаунт Docker.

* **`trivy-action` вместо запуска образа:**
  * *Плюсы:* короче YAML.
  * *Минусы:* действие по изменяемому тегу — ещё одна точка атаки на цепочку поставки; образ по digest проверяем тем же способом, что hadolint.

* **Только документация про rootless:**
  * *Плюсы:* ноль минут CI.
  * *Минусы:* без проверки любое изменение образа может незаметно сломать запуск без root.

## Последствия

### Положительные

* [+] Скомпрометированный `web` не может обратиться в интернет через `backend` и не видит redis снаружи; `migrate` и `seed` вообще без сети.
* [+] Админка без логина недоступна из сети, пока это не сделано осознанно.
* [+] Ослабление изоляции в compose ломает CI, а не проходит ревью незамеченным.
* [+] Для каждого релиза есть образ по digest, SBOM, аттестация происхождения и еженедельный отчёт об уязвимостях.

### Отрицательные

* [-] Первый прогон Trivy может найти исправимые CVE в зависимостях и уронить CI до обновления или исключения.
* [-] Плюс один job (`podman`) и сканирование: несколько минут CI при изменении образа.
* [-] Пакет в GHCR после первой публикации нужно один раз сделать публичным или выдать доступ вручную.
* [-] Версия Trivy задана в двух workflow и обновляется вручную: Dependabot не отслеживает образы в переменных workflow.
