# ADR 0004: Hardening контейнеров и токен бота как Docker secret

## Дата: 19-11-2026

## Статус: Accepted

## Контекст

Бот обрабатывает персональные данные студентов (имя, телефон, группа), а его токен даёт полный контроль над ботом: с ним можно читать входящие сообщения и писать пользователям от имени бота. Если в зависимостях или в коде окажется уязвимость, важно, что атакующий получит внутри контейнера.

До этого решения:

1. Образ уже собирался без root (uid 1000) и с базовым образом, закреплённым по digest.
2. Корневая файловая система контейнеров была доступна на запись, Linux capabilities оставались по умолчанию.
3. `BOT_TOKEN` проверялся при импорте конфигурации, поэтому его получал каждый процесс: веб-сервер, миграции, загрузка модели. Через `env_file` токен виден в `docker inspect` любого из этих контейнеров.
4. uid 1000 совпадает с первым пользователем большинства Linux-хостов: файлы, созданные контейнером в bind mount, принадлежат этому пользователю, и наоборот.
5. redis запускался от root (entrypoint понижает права сам) и тегом без digest.

## Решение

Принято решение запускать все сервисы с минимальными правами и передавать токен только боту через Docker secret.

### Детали реализации

1. **Пользователь.** Системный `app` с uid/gid 10001, без домашнего каталога и shell. Код и виртуальное окружение принадлежат root, приложение их только читает.
2. **Read-only ФС.** `read_only: true` и `tmpfs: /tmp` у всех сервисов. Писать можно только в тома: `app-data` (SQLite), `hf-cache` (модель), `redis-data`. `HOME=/tmp`, `PYTHONDONTWRITEBYTECODE=1`. В dev-override у `web` и `bot` корень доступен на запись, иначе не работает `docker compose watch`.
3. **Capabilities.** `cap_drop: [ALL]`, `no-new-privileges:true`; `privileged` не используется. redis запускается от своего пользователя (`999:1000`), поэтому entrypoint не делает chown и su-exec.
4. **Секреты.** `config` читает `BOT_TOKEN` и `TELEGRAM_PROXY_URL` из `*_FILE`, если переменная задана. Токен — Docker secret из `./secrets/bot_token`, смонтирован только в `bot`. Во всех контейнерах `BOT_TOKEN` из `.env` явно обнуляется. Токен проверяется при старте бота (`config.require_bot_token()`), а не при импорте.
5. **Данные.** SQLite переезжает из bind mount `./data` в именованный том `app-data`, который при первом использовании получает владельца 10001 из образа.
6. **Лимиты.** `cpus`, `memory` и `pids_limit` у каждого сервиса; `restart: unless-stopped` для долгоживущих сервисов.
7. **Цепочка поставки.** Образы `python` и `redis` закреплены по digest, Dependabot обновляет оба (`docker`, `docker-compose`). `.dockerignore` исключает `.env`, `secrets/`, ключи, сертификаты и дампы.
8. **Проверки в CI.** Импорт приложения и миграции запускаются с теми же ограничениями (`--read-only --cap-drop ALL ...`) и без токена; бот без токена обязан не стартовать; в слоях образа не должно быть `.env`, `secrets/` и переменных, похожих на секреты.

## Альтернативы

* **Оставить uid 1000 и bind mount `./data`:**
  * *Плюсы:* база лежит файлом рядом с проектом, её легко открыть.
  * *Минусы:* uid совпадает с пользователем хоста; при смене uid на 10001 bind mount требует `chown` на хосте.

* **Токен через `env_file`:**
  * *Плюсы:* проще, соответствует 12 Factor (конфигурация в окружении).
  * *Минусы:* токен виден в `docker inspect` и в окружении дочерних процессов, и получают его все сервисы.

* **Distroless-образ или `scratch`:**
  * *Плюсы:* нет shell и пакетного менеджера.
  * *Минусы:* сложнее отладка и healthcheck; основной объём образа — torch, а не ОС. Вернуться к этому после B8a (ONNX вместо torch).

## Последствия

### Положительные

* [+] Взлом `web` (самый открытый сервис) не даёт токен бота.
* [+] Нельзя изменить код или поставить пакеты внутри работающего контейнера.
* [+] Утечка памяти или fork bomb в одном сервисе ограничены его лимитами.

### Отрицательные

* [-] Перед первым запуском нужно создать `secrets/bot_token`.
* [-] База больше не лежит в `./data`: доступ через `docker compose cp` или `run`.
* [-] Библиотека, которая пишет вне `/tmp` и томов, упадёт с `Read-only file system`. CI ловит это для импорта и миграций, но не для каждого пути исполнения.
